# `/rule` Slash Command Specification

## Overview

The `/rule` slash command allows developers to generate FinCEN validation rules using natural language descriptions. It automatically creates both the rule implementation and comprehensive feature tests following the project's established patterns.

## Command Syntax

```
/rule [REPORT_TYPE] [NATURAL_LANGUAGE_DESCRIPTION]
```

### Parameters

- **REPORT_TYPE**: Either `GTO` or `RER` (case insensitive)
- **NATURAL_LANGUAGE_DESCRIPTION**: Plain English description of the validation rule

### Examples

```bash
/rule GTO All top level entities must be EntityType::ENTITY and each of their children must be EntityType::PERSON
/rule RER Buyer entities must have a valid TIN when from the US
/rule GTO Property address must be complete with street, city, state, and zip
/rule RER Seller must provide either SSN or EIN depending on entity type
```

## Command Processing Workflow

### 1. **Input Parsing**
- Extract report type (GTO/RER)
- Parse natural language description
- Identify key entities, fields, and validation logic

### 2. **Pattern Recognition**
The command analyzes the description for common patterns:

#### Entity Validation Patterns
- `"all top level entities must be [TYPE]"`
- `"[ROLE] entities must be [TYPE]"`
- `"children must be [TYPE]"`
- `"no third level entities"`

#### Field Validation Patterns
- `"[FIELD] must be [CONDITION]"`
- `"[FIELD] is required when [CONDITION]"`
- `"[FIELD] must be valid [FORMAT]"`

#### Relationship Validation Patterns
- `"at least one [ENTITY] required"`
- `"[ENTITY] must have children"`
- `"[ENTITY] cannot have [FIELD]"`

### 3. **Rule Classification**
Automatically determines the appropriate section based on content:
- **buyer_details**: Rules about buyer/transferee entities
- **seller_details**: Rules about seller/transferor entities
- **property_details**: Rules about property information
- **filer_details**: Rules about firm/filer information
- **payment_details**: Rules about payment information

### 4. **Clarification Questions**
If the rule description is ambiguous, Claude will ask:
- Which validation section should this belong to?
- What should be the specific error message?
- Should this apply to all entities or specific transfer roles?
- What constitutes a "valid" value for complex validations?

### 5. **File Generation**
Creates two files:
1. **Validation Rule**: `api/app/Validators/Reports/Rules/[TYPE]/[Section]/[RuleName]Rule.php`
2. **Feature Test**: `api/tests/Feature/Validators/Reports/Rules/[TYPE]/[Section]/[RuleName]RuleTest.php`

### Validation Pattern Templates

#### Entity Type Validation
**Patterns**:
- `"all top level entities must be {entityType}"`
- `"top level entities must be {entityType}"`
- `"{role} entities must be {entityType}"`
- `"each {role} must be {entityType}"`
- `"children must be {entityType}"`
- `"second level entities must be {entityType}"`

**Generated Code Template**:
```php
if ({entityType} !== $entity->type) {
	return ValidationResult::failure(
		"entities.{$index}.type",
		'{errorMessage}'
	);
}
```

#### Hierarchy Validation
**Patterns**:
- `"no third level entities"`
- `"entities cannot have grandchildren"`
- `"maximum two levels of entities"`
- `"at most {count} levels deep"`

**Generated Code Template**:
```php
if (isset($entity->children)) {
	foreach ($entity->children as $child) {
		if (isset($child->children) && $child->children->isNotEmpty()) {
			return ValidationResult::failure(
				"entities.{$index}.children.{$childIndex}.children",
				'{errorMessage}'
			);
		}
	}
}
```

#### Required Field Validation
**Patterns**:
- `"{field} is required"`
- `"{field} must be provided"`
- `"{field} cannot be empty"`
- `"{field} is required when {condition}"`

**Generated Code Template**:
```php
if ($this->isEmpty($entity->{field})) {
	return ValidationResult::failure(
		"entities.{$index}.{field}",
		'{errorMessage}'
	);
}
```

#### Relationship Validation
**Patterns**:
- `"at least one {role} required"`
- `"must have at least {count} {role}"`
- `"{role} must have children"`
- `"{role} must have at least one child"`

**Generated Code Template**:
```php
if ($entities->isEmpty()) {
	return ValidationResult::failure(
		"entities",
		'{errorMessage}'
	);
}
```

#### Conditional Validation
**Patterns**:
- `"{field} is required when {condition}"`
- `"if {condition} then {field} must be {value}"`
- `"{field} must be {value} when {condition}"`

**Generated Code Template**:
```php
if ({condition} && {validation}) {
	return ValidationResult::failure(
		"entities.{$index}.{field}",
		'{errorMessage}'
	);
}
```

## Implementation Examples

### Example 1: Entity Hierarchy Rule
**Input**: `/rule GTO All top level entities must be EntityType::ENTITY and each of their children must be EntityType::PERSON`

**Generated Rule Logic**:
```php
// Check top-level entities
foreach ($report->entities as $index => $entity) {
	if (EntityType::ENTITY !== $entity->type) {
		return ValidationResult::failure(
			"entities.{$index}.type",
			'Top level entities must be of type ENTITY'
		);
	}

	// Check children
	if (isset($entity->children)) {
		foreach ($entity->children as $childIndex => $child) {
			if (EntityType::PERSON !== $child->type) {
				return ValidationResult::failure(
					"entities.{$index}.children.{$childIndex}.type",
					'Second level entities must be of type PERSON'
				);
			}
		}
	}
}
```

### Example 2: Required Field Rule
**Input**: `/rule RER Buyer entities must have a valid TIN when from the US`

**Generated Rule Logic**:
```php
$buyers = $report->entities->filter(function ($entity) {
	return TransferRole::BUYER === $entity->transfer_role;
});

foreach ($buyers as $index => $buyer) {
	if ($buyer->country === 'US' && $this->isEmpty($buyer->tin)) {
		return ValidationResult::failure(
			"entities.{$index}.tin",
			'US buyer entities must have a valid TIN'
		);
	}
}
```

## Test Generation Patterns

For each rule, the following test methods are automatically generated:

### Standard Test Methods
1. **`test_passes_for_valid_[scenario]`**: Happy path validation
2. **`test_fails_for_invalid_[scenario]`**: Error condition testing
3. **`test_ignores_non_[report_type]_reports`**: Report type filtering
4. **`test_handles_empty_entities_gracefully`**: Edge case handling

### Entity-Specific Tests
- **Hierarchy rules**: Test valid/invalid parent-child relationships
- **Type rules**: Test all relevant entity types
- **Required field rules**: Test missing vs present fields
- **Conditional rules**: Test various condition combinations

### Test Data Generation Templates

#### Entity Type Tests
```php
// Valid test setup
Entity::factory()->create([
	'type' => {validType},
	'report_id' => $report->id
]);

// Invalid test setup
Entity::factory()->create([
	'type' => {invalidType},
	'report_id' => $report->id
]);
```

#### Hierarchy Tests
```php
// Valid hierarchy
$parent = Entity::factory()->create(['report_id' => $report->id]);
Entity::factory()->create(['parent_id' => $parent->id, 'report_id' => $report->id]);

// Invalid hierarchy (three levels)
$parent = Entity::factory()->create(['report_id' => $report->id]);
$child = Entity::factory()->create(['parent_id' => $parent->id, 'report_id' => $report->id]);
Entity::factory()->create(['parent_id' => $child->id, 'report_id' => $report->id]);
```

#### Required Field Tests
```php
// Valid field test
Entity::factory()->create([
	'{field}' => 'valid_value',
	'report_id' => $report->id
]);

// Invalid field test
Entity::factory()->create([
	'{field}' => null,
	'report_id' => $report->id
]);
```

## Integration with Existing System

### Automatic Discovery
Generated rules are automatically discovered by `RuleDiscoveryService` through:
- File naming convention (`*Rule.php`)
- Namespace structure
- Attribute-based section classification

### Validation Integration
Rules are executed by:
- `GtoRuleValidator` for GTO rules
- `RerRuleValidator` for RER rules
- `RuleOrchestrator` for coordinated validation

### Cache Invalidation
After generating new rules:
- Clear validation rules cache: `RuleDiscoveryService::clearCache()`
- Regenerate rule mappings for immediate availability

## Command Error Handling

### Common Errors
- **Invalid report type**: "Report type must be either GTO or RER"
- **Empty description**: "Rule description cannot be empty"
- **Ambiguous description**: Claude will ask clarifying questions
- **File conflicts**: Check for existing rules with same name

### Fallback Behavior
If natural language processing fails:
- Ask for clarification with specific questions
- Provide examples of well-formed rule descriptions
- Offer to create a basic template for manual completion
